# plan_MILEAGE — правило «пробег не больше 400 000 км, иначе review»

Задача: при расчёте решения по заявке пробег авто не больше 400 000 км; при
превышении решение — `review`. Источники: формулировка заказчика и
`docs/setup/code_map.md` (раздел «Куда встанет правило…»). Сегодня влияние
пробега на решение отсутствует полностью: после валидации он просто переносится
в `input` (`code_map.md:58–63`).

Принятая семантика — буквальное чтение требования: `mileage > 400000` → `review`
безусловно, проверка ставится **до** LTV-веток и перекрывает и потенциальный
`approve`, и `reject`. Граница включительная: 400 000 — ещё допустимый пробег.
Альтернатива («пробег понижает только approve, reject сохраняется») — в «Рисках»
и «Вопросах»; смена варианта — одна строка порядка проверок плюс один тест.

Порог — новое число в `backend/config/rules.php` по конвенции проекта.
Существующий `vehicle.max_mileage_km = 500000` — граница **валидации**
(`ApplicationValidator.php:43–46`), смысл не меняется и не переиспользуется.

Заменяет устаревший черновик `docs/plan/mileage.md` (не по конвенции имён
`plan_<ID>.md`); при ревью его следует удалить.

## Риски

- **Существующая проверка `max_mileage_km`**: главный риск — спутать два порога.
  Переиспользовать `vehicle.max_mileage_km` или «снизить» его до 400000 нельзя:
  тогда заявки с пробегом 400001–500000 начнут получать 422-ошибку валидации
  вместо решения `review`, молча меняя контракт API и ломая тесты охраны.
  Новый ключ обязан жить отдельно и под другим именем.
- **Перекрытие reject**: буквальная семантика ослабляет кредитное правило —
  заявка с LTV 120% и пробегом 400001 получает `review`, а не `reject`. Если
  заказчик имел в виду понижение только `approve`, а уточнение придёт после
  реализации, правило меняется в одну строку, но уже сохранённые в БД решения
  пересчитаны не будут.
- **Сигнатура `decide()`**: вызовов ровно два — `AssessmentService.php:33` и
  `DecisionEngineTest.php:23` (проверено поиском по репозиторию, включая
  `mocks/`; других нет). Пропуск любого → `TypeError`, поэтому правим в порядке
  шагов 2→4.
- **Граница «не больше»**: включительная; ошибка `>` вместо `>=` — типичный
  off-by-one. Пинается тройкой 399999 / 400000 / 400001 на двух уровнях.
- **Регрессия существующих тестов**: фикстуры используют пробеги 96000 и 84000 —
  ниже порога, ожидания меняться не должны. Если пришлось править их ожидания —
  правило протекло в валидацию или LTV.
- **LTV-граница 60.0/85.0**: в коде несогласованность докблоков и `<`
  (`code_map.md:41`) — не наш фикс; новые тесты берут LTV 50.0 / 72.3 / 120.0.
- **«Пустой пробег» с фронта**: `frontend/app.js` приводит поле к числу — пустое
  поле уйдёт в API как `0`, а не как отсутствующее: бэкендная ветка «отсутствует
  → 422» работает только для прямых API-клиентов, а для формы правило пробега
  на таких заявках не сработает (пробег 0 ≤ порога). Поведение объяснено в
  Вопросе 2, само по себе не ломается.
- **Сохранённые решения**: решение фиксируется в БД при `POST /api/applications`;
  введённое правило не пересчитывает существующие строки. Сид-данные
  противоречий не создают — максимальный пробег в `db/seed.sql` равен 296000.
- **Не входит**: фронтенд, схема БД/`seed.sql`/репозиторий, фикс несогласованности
  LTV `<` / `<=`, лимит по возрасту (LOAN-12), пересчёт старых решений, поле
  причины `review` в ответе API, любые тексты ошибок валидации.
